UI-CLEAN-ARCH / LIVING NOTEBOOKv0.42 · English edition
01 / purpose

An explicit architecture. A verifiable implementation.

Frontend architecture for building UI, with abstractions, boundaries, and organization developed together.

Goal: reduce implicit decisions and rework when creating or refactoring with a skill.

Starting point: the author's diagram
02 / confirmed in the diagram

Four abstractions.

The arrangement runs from Components on the outside to Entities at the center.

At this stage of the discussion, responsibilities, dependencies, and flow still needed the author's definitions.

03 / developing the vocabulary

Names are the beginning.

ComponentsUI: meaningful sections composing the screen.
StoresConnect Components through actions and changes; retrieve and persist screen state.
ServicesExternal integrations; object input and always asynchronous output.
EntitiesAdapt and format data for semantic UI consumption.
04 / proposed method

From knowledge to actionable rules.

  1. Define application scope and choose a reference feature.
  2. Define responsibilities and walk through a complete flow.
  3. Map abstractions to folders and resolve ambiguous cases.
  4. Write the skill and evaluate creation and refactoring with examples.

A proposed working method, not itself an architectural rule.

05 / skill quality

Every rule must guide a decision.

Record what to do, in which situation, why, and how to verify the result.

Examples and counterexamples should clarify where a responsibility belongs.

The goal is observable reliability. No accuracy percentage has been measured or guaranteed.

06 / confirmed scope

Frontend. UI. Framework independence.

The architecture should work with any framework and be as agnostic as possible.

Framework-specific elements may exist in Components and in appropriate auxiliary abstractions.

The precise limits are recorded later. Abstractions were defined individually, one at a time.

08 / Components · confirmed

The section is the unit of composition.

Components are meaningful, contextual sections composing the entire screen. The division is semantic and independent of visual arrangement.

Each section aggregates its content and may import smaller reusable components.

Author-defined scope: any screen, business, or frontend web application.

09 / reading the whole screen

Six sections. One screen.

  1. Header — upper green area and its contents.
  2. Account balance — the entire card.
  3. Action menu — Pix, Pay, Transfer, and More.
  4. Cards — the entire card.
  5. Recent transactions — title, list, and other contents.
  6. Footer — bottom navigation and green background.
10 / responsibility · confirmed

Components handle UI and local interaction.

They may listen for events and change internal state when effects stay within the section and require no persistence.

For persistence or propagation across Components, connect the event to an external action and render received state.

Buttons, icons, and reusable items may compose a section internally. The section aggregates these in a larger context.

The following definitions explain how Stores, Services, and Entities connect to Components.

11 / context and layout · confirmed

Same context. Same abstraction.

Cards and Recent transactions remain two Components on desktop and mobile, whether side by side or stacked.

A container wraps the pieces and arranges them. It has no architectural abstraction value.

Criterion: identify sections by context, not by position or breakpoint.

12 / decision · confirmed

The effect's reach determines the boundary.

Local state

Hide only the balance in its own card, without persistence.

The Component listens for the event, changes state, and renders.

External action

Persist the preference or also hide amounts in Cards and other sections.

The Component connects the event to the action and renders received state.

13 / persistence · confirmed

Retaining the latest state is a requirement.

Persistence is needed when behavior must retain its latest state using local capabilities or remote backend storage.

If business rules allow losing state when returning to the screen or reloading, persistence is not required.

Even without persistence, propagation to other Components requires an external action.

14 / composition levels · confirmed

Structural and atomic elements are components.

The screen-level abstraction refers to structural sections. Each section internally composes smaller atomic components.

Their files must not be siblings of structural component files at screen level. Both can belong to the same encompassing folder.

The precise hierarchy is defined in the folder-structure sections. No tree had been fixed at this point in the discussion.

15 / Stores · confirmed

An action connects the sections.

The Store connects Components when behavior must be reacted to and updated across them in response to an action.

It is also responsible for retrieving and persisting screen state.

Retrieval and persistence invoke an external capability. The Service definition establishes that integration boundary.

16 / Store capabilities · confirmed

Read changes. Execute actions.

Reading

The Component imports a capability to listen for changes and update local state.

It has access to state and the action that triggered the change.

Writing

The Component imports a capability to execute an action with optional parameters.

The Store uses this information to determine the next state.

17 / Store boundary · confirmed

Invoke persistence through an external capability.

The Store initiates state retrieval and persistence without directly accessing local storage or the backend.

The Service contract below defines the integration boundary; concrete application contracts remain scenario-specific.

18 / scope and reuse · confirmed

One Store per screen.

Each screen owns its Store. Behavior needed by multiple screens is reused through shared actions.

Actions may be functions or objects containing functions.

Goal: greater decoupling and autonomy so each screen is more standalone.

19 / action contract · confirmed

Current state → action → next state.

The Store supplies current state and optional parameters to the action function. The action returns the next state to the Store.

The Store notifies registered listeners with the action and complete updated screen state. Listening Components may update their UI.

Objects may organize action functions. Mutation or immutability depends on the library; actions may invoke external capabilities and await their results.

20 / notification contract · confirmed

An action may change a part. Listeners receive the whole.

Notifications provide the action and total screen state after the update, even when only part changed.

Mutation or immutability is a Store-library implementation detail. Both are allowed.

Verification criterion: listeners receive complete updated state, not only changed fields.

21 / relevant reactions · confirmed

React when the change matters.

The Store may provide information such as the called action so the Component can decide whether to react, or simplify registration for relevant actions only.

The choice depends on the library and application. The goal is to avoid unnecessary rendering.

The contract remains: action and complete updated screen state. Selection does not mandate a specific API.

22 / asynchronous actions · confirmed

Await a result to produce state.

An action may invoke an external capability and await its result before producing the next state.

The Store remains responsible for notifying listeners with the action and complete updated state.

Asynchronous actions are allowed, not required for every action. External integrations follow the Service definition.

23 / Services · confirmed

An external integration capability.

Services abstract integrations with pieces or APIs external to the application.

localStorage access and backend API requests must go through Services.

Integration stays encapsulated even when the underlying resource is synchronous.

24 / Service contract · confirmed

One object in. A Promise out.

Input: exactly one parameter, an object with named properties.

Output: always a Promise of an object or a list of objects.

A single parameter makes the contract easier to extend and reduces changes to positional parameter sequences. Every Service is asynchronous.

25 / integration boundary · confirmed

Integrations go through Services.

Components and Stores never access capabilities such as fetch or localStorage directly. Access is always mediated by a Service, including within actions.

The user and application define the concrete return-object format for the scenario.

The architecture requires a Promise of an object or list of objects without imposing a particular result envelope.

26 / Service form · confirmed

Access functions. No retained state.

Services are functions, not classes. They provide read and write access to external resources and APIs.

They do not persist information within themselves or retain local state between calls.

Persisting through a Service means writing to the external resource, such as localStorage or a backend. The Service is not storage.

27 / Entities · confirmed

Data prepared for the UI.

Entities adapt external data shapes into a semantic, application-friendly format. Components should not need to format these data.

They are functions with one object input, properties destructured in the signature, and default values.

The recognizable design includes functions such as Product and ProductPrice identified by an @Entity comment.

28 / composition · confirmed

Service retrieves. Entity adapts.

A Service may pass a retrieved object to an entity and return the result. For lists, it may map the entity over items.

Entities can compose and coexist in one file: Product uses ProductPrice to provide raw price, discount, and formatted value.

Example fields and defaults are scenario-specific, not universal application-data rules.

29 / Entity validation · confirmed

Handle null where data is used, when needed.

The Entity using information should handle accesses that could fail on null according to the scenario.

The user or developer assesses validation needs and confidence in the data contract. Checking every field is not mandatory.

Destructuring defaults cover missing values and undefined, not explicit null. The signature alone does not guarantee null safety.

30 / Entity purity · confirmed

Transform synchronously and purely.

Entities only transform received data. They retain no state, do not modify inputs, and perform no external effects.

The same inputs produce the same result. Entity composition preserves this contract.

This rule applies to Entities. Store state mutation strategy remains a library implementation detail.

31 / next stage

From responsibilities to folders.

Define where each abstraction lives, how a screen is organized, and how resources are shared.

The structure was developed from the author's decisions. No pre-existing directory architecture was adopted as a default.

32 / one domain per screen · confirmed

Each screen is a domain.

Each screen owns its domain. Exclusive abstractions are colocated for easier access and discovery.

In this architecture, domain means screen. The store folder still represents one Store per screen.

33 / structure and extensibility

domain / statement

What is screen-specific and used only there belongs in its domain.

constants and formatters are optional auxiliary-folder examples. The following slides define internal organization.

domain/
└── statement/
    ├── components/
    ├── services/
    ├── entities/
    ├── store/
    ├── constants/
    └── formatters/
34 / extensibility · confirmed

Four abstractions. Room for more folders.

Components, Stores, Services, and Entities are official abstractions. Application organization may include auxiliary folders for specific needs.

constants and formatters illustrate this option; they are not architectural abstractions or mandatory directories.

Create auxiliary folders for concrete needs rather than imposing the example tree as a universal checklist.

35 / Component organization · confirmed

One folder per section. An index entry.

The index composes the section and imports internal or external atomic components. Its extension follows the application's technology.

Atomic files live inside the structural folder. .extension is only a placeholder.

components/
├── header/
├── balance/
├── menu/
├── cards/
│   ├── index.extension
│   ├── invoice.extension
│   └── due-date.extension
├── transactions/
└── footer/
36 / optional extraction · confirmed

Extract when there is a reason.

A structural folder may contain only index. Separate files for internal elements are not mandatory.

Extraction is suggested for extensive code or strongly justified reuse in the screen tree.

The developer decides. Cross-section reuse requires assessing coupling and independent evolution.

37 / reuse within a domain · confirmed

The atomic component stays with its owner.

The developer identifies the structural owner. Another structural component in the same domain may import it from there with strong justification for coupling.

Do not move atomic components to the screen root or structural level to enable reuse.

This rule concerns sharing within one domain.

38 / section autonomy · confirmed

Duplication can preserve independent evolution.

Similar HTML does not require sharing. Duplication may better support sections evolving independently.

Reuse across structural components must provide a strong enough benefit to justify the dependency.

Avoid extraction and centralization motivated only by mechanical deduplication.

39 / cross-domain sharing · confirmed

shared is a sibling of domain.

Reserved specifically for cross-domain reuse. It organizes the same abstractions, like a screen without UI.

Exclusive resources remain in their domain. shared is not a catch-all for code without a clear home.

domain/
└── ...
shared/
├── components/
├── store/
├── services/
└── entities/
40 / shared/store · confirmed

Share actions. Preserve each screen's Store.

shared/store holds shareable actions used by domain Stores.

Each domain keeps its own Store and state. This folder does not represent a common state Store across screens.

Behavior is reused while each screen retains autonomy.

41 / dependencies · confirmed

Domains depend on shared.

A domain may import shared resources. It must never import directly from another domain.

shared does not import domain resources and must not know domains exist.

Review criterion: allow domain → shared; prevent domain A → domain B and shared → domain.

42 / layer dependencies · confirmed

Outside to inside, with direct access.

SourceMay import
ComponentsStores, Services, Entities
StoresServices, Entities
ServicesEntities
EntitiesNo outer layer

Reverse dependencies are forbidden. Intermediate layers do not have to be traversed.

43 / applying the rules together

Permitted access. Preserved responsibilities.

Components may import Services and Entities directly when needed. Integrations remain encapsulated in Services.

Persistence or behavior propagation across Components still uses the Store according to its contract.

Layer permissions do not authorize cross-domain imports or shared → domain dependencies. Confirmed same-layer composition remains valid.

44 / screen composition · confirmed

The domain index composes the screen.

The index file at the domain root imports structural components and composes the entire screen.

Each index inside components composes its own section. The extension follows the technology.

domain/
└── statement/
    ├── components/
    ├── services/
    ├── entities/
    ├── store/
    ├── ...
    └── index.extension
45 / Store organization · confirmed

One Store. A singular folder name.

statement.extension implements the Store. actions.extension contains the actions it imports.

The Store internally determines what should happen.

The store convention replaces stores throughout the structure. shared/store keeps shareable actions.

domain/
└── statement/
    └── store/
        ├── statement.extension
        └── actions.extension
46 / Service organization · confirmed

A folder with an index entry.

Each Service grouping occupies a folder. The developer may keep its functions in index or split them into internal files.

http and statement are examples. The extension depends on implementation.

services/
├── http/
│   └── index.extension
└── statement/
    └── index.extension
47 / Service composition example

A wrapper may encapsulate transport.

http may abstract fetch or a library such as axios. statement may group integration functions for that context.

These are examples, not mandatory pieces. Service contracts and domain/shared placement rules still apply.

48 / Entity organization · confirmed

The same convention as Services.

Each Entity grouping has a folder and index entry. Complementary functions may share a file or be split into internal files.

Product and ProductPrice may stay together, composing the data adaptation.

Organization does not change the contract: pure, synchronous, stateless functions receiving one destructured object.

49 / shared/components · confirmed

Structural and atomic components at the same level.

Both may occupy the same level in shared/components without mandatory category distinction.

This rule is specific to shared. Within domains, extracted atomic components remain with their structural owner.

50 / state in shared components · confirmed

The parent supplies state.

The parent instantiating a shared component supplies props or injects a Store.

That parent may be the screen-composition index or a structural component.

Store injection does not authorize importing a domain. shared remains unaware of the domains using it.

51 / framework integration · confirmed

Placement and routes follow the technology.

src is a suggested home for domain and shared. Actual placement and route files depend on the framework.

The architecture imposes no universal routing or code-root convention.

52 / application shell · confirmed option

layouts/default may wrap screens.

A layout may compose the application shell with recurring structural elements around screens.

It may use shared components such as headers and footers as needed.

layouts/default.extension is optional, not a fifth abstraction or mandatory file. Exclusive elements stay in their domain.

53 / framework coupling · confirmed

Of the four layers, only UI depends on the framework.

Components may use the UI framework. Stores, Services, and Entities remain independent.

Developers may create auxiliary abstractions as needed, and these may be coupled to the framework.

Store implementation freedom does not allow UI-framework dependencies in the official inner layers.

54 / skill modes · confirmed

Create from scratch or migrate completely.

Creation: build the application with the complete architecture.

Refactoring: fully apply the architecture to an existing application while preserving behavior and functionality.

Staged execution may support migration; the expected outcome remains complete.

55 / migration verification · proposed

Functional preservation needs evidence.

Map screens, behavior, and integrations before changing them. Verify architecture and compare behavior after migration.

Proposed skill procedure, later consolidated. Refactoring does not authorize feature or business-rule changes.

56 / questions and autonomy · confirmed

Ask about decisions that change the product.

Ask the developer when a missing decision affects product or behavior.

Resolve implementation details through context, respecting architecture and application conventions.

When refactoring, inspect existing behavior first. Do not repeat answered questions or invent missing requirements.

57 / ui-clean-arch

First version consolidated.

The local package brings together contracts, structure, and creation/refactoring modes.

Structural skill validation passed. Application reliability still needs behavioral evaluation.

Next: apply the skill to concrete scenarios and fix demonstrated ambiguities without accumulating speculative rules.

60 / premise · confirmed

Readability is part of the architecture.

Prioritize understanding with consistent indentation, spacing, and line breaks revealing logic and composition.

Avoid compressed code across layers, including UI, styles, and tests. Separate steps visually without imposing a line limit or specific tool.

Readability review is part of completion. Generated or minified distribution artifacts are exceptions.
